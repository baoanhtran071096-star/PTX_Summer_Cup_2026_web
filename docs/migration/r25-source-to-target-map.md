# R25 → Target Source-to-Target Map

> **Module:** M-02 — Extraction & Migration Mapping
> **Depends on:** `docs/legacy/r25-*-inventory.md` (M-01, frozen).
> **Purpose:** Map every meaningful legacy source to its explicit target ownership in the Next.js + Supabase architecture. Nothing meaningful may be left unmapped.

## Important context established during extraction

`ptx_migration_data.json` (exportVersion "2.4", exported 2026-07-30) is **stale relative to the live `index.html` (R25-PRODUCTION)**: its player `avatar` fields are still `postimg.cc` hotlink URLs, while the live `PLAYERS_DATA` in `index.html` (lines 6311+) already uses localized `thư viện/Ảnh cầu thủ/*.webp` paths (the R14 asset-localization changelog). **`index.html`'s inline `TEAMS_DATA`/`PLAYERS_DATA`/`MATCHES_CONFIG` are the authoritative extraction source for team/player/match roster data — not the JSON file.** The JSON file remains useful only for its `localStorage` block (tournament settings, Hall of Fame, gallery override), which is not duplicated inline in `index.html`.

Also established: as of this snapshot the tournament has **not yet been played** — all players show `goals: 0, assists: 0, mvp: 0`, all `ptx_result_*` keys are presumably unset/empty (no match has occurred; matches are scheduled 2026-08-07, current date at time of this migration is 2026-08-04). This significantly reduces migration risk for match-history data — there is no real historical match/goal/card data to lose, only roster/config data and whatever the admin has entered so far. The reconciliation plan still treats this formally (do not assume — verify against the live admin's actual current localStorage/Firestore state before declaring "nothing to migrate").

## Map

| Legacy source | Target ownership | Notes |
|---|---|---|
| `TEAMS_DATA` (index.html:6302-6309) | Postgres `teams` table | 3 rows (`p`,`t`,`x`). `logo` path → Supabase Storage `team-logos/` bucket. |
| `PLAYERS_DATA` (index.html:6311-6552) | Postgres `players` table | 24 rows. `avatar` path → Supabase Storage `player-avatars/` bucket. Static `goals`/`assists`/`mvp` counters → **NOT copied as mutable columns**; target computes these from `match_events` (see reconciliation plan §3, MODERNIZE decision) to satisfy the "Match Results is source of truth" rule extended to player stats. Initial values (currently all 0) need no seed since aggregation over zero events naturally yields 0. |
| `ptx_players_data` localStorage override (admin edits) | Same `players` table | If the live admin browser has edits beyond the roster baked into `index.html`, these override values (not the static `index.html` copy) are authoritative — must be extracted from the live admin's browser/export before cutover, not reconstructed from `index.html` alone. |
| `MATCHES_CONFIG` (index.html:6563-6567) | Postgres `matches` table | 3 rows. `startH/startM/endH/endM` + global `baseDate` (`2026-08-07`) → combined into `match_date` + `start_time`/`end_time` columns. |
| `ptx_result_<id>` pipe-string (localStorage/Firestore) | Postgres `match_events` table (+ derived `matches.home_score`/`away_score` via aggregation, not stored redundantly) | Parsed per the format in `r25-data-inventory.md` §1.4: score prefix → not stored directly (derived from event count), scorer tokens → one `match_events` row each (`event_type='goal'`, `player_id` resolved by name-match against target `players`, `minute`). **No assist/card data exists in the legacy string** — target `match_events` rows are goal-only from this source; assist/card capture becomes a genuinely new (not migrated) data-entry capability for the admin panel going forward. |
| `ptx_stat_goals/matches/players/yellow/red` (tournament-wide counters) | Derived aggregates (view/query over `matches`+`match_events`), not stored columns | Same "don't duplicate a source of truth" rule. |
| `ptx_slogan`, `ptx_msg`, `ptx_date`, `ptx_location` | Postgres `tournament_settings` single-row table | Free text, direct 1:1 copy. |
| `hof_<year>` pipe-string | Postgres `hall_of_fame` table | 5 positions → `champion_team_id`, `runner_up_team_id`, `third_place_team_id` (nullable FK to `teams`), `golden_boot_player_id`, `mvp_player_id` (nullable FK to `players`). Legacy placeholder text `"Chưa đủ dữ liệu (Cập nhật sau)"` (seen in `hof_2025`) maps to **NULL**, not a copied placeholder string — UI renders "TBD"/"Chưa xác định" for NULL fields instead of storing magic strings. |
| `GALLERY_ITEMS` (static array) + `gallery_<year>` override | Postgres `gallery_media` table + Supabase Storage `gallery/` bucket | Each of the 3 pipe-delimited URLs per year → 1 row (`category`: opening/matchday/awards). Any remaining `postimg.cc` URLs (e.g. `gallery_2025` in the JSON snapshot) must be downloaded and re-hosted in Storage — see asset migration plan. |
| `GALLERY_PAGE_ITEMS` (dedicated gallery page) | Same `gallery_media` table | Reconcile against `GALLERY_ITEMS` for duplicates before import. |
| `ptx_user_prediction`, `ptx_user_predictions_list`, `SAMPLE_PREDICTIONS` | Postgres `predictions` table | Per-visitor, browser-local, never cloud-synced (confirmed in M-01). **There is no server-side copy to extract** — these exist only in whichever browser last held them. Nothing to bulk-migrate; only the *shape*/rules carry forward (see reconciliation plan §4). `SAMPLE_PREDICTIONS` (demo seed data) is explicitly demo content, not real user data — DEPRECATE, do not seed the new product with fake predictions presented as real. |
| `ptx_admin_user`/`ptx_admin_hash`/`ptx_salt` (single hardcoded admin) | Supabase Auth user + `profiles` table (`role='admin'`) | See auth transition plan — this is a re-platform of the *mechanism*, not a data copy (password hash format is incompatible/insecure and must not be carried over as-is). |
| Firestore `tournamentState` collection (`results`/`stats`/`eventInfo` docs) + `players` doc | Superseded entirely by Postgres + Supabase Realtime | Firebase/Firestore is fully retired, not dual-run. `firestore.rules` is reference-only (already audited in M-01). |
| `thư viện/` media tree | Supabase Storage buckets | See `r25-asset-migration-plan.md` for the full folder→bucket mapping. |
| `database_schema.sql` draft tables `chat_messages`, `notifications` | **No target in v1** — Approved Deprecation Registry (M-03) | Zero corresponding live feature (M-01 finding); do not build unused tables. |
| Legacy "chat" DOM widget (ephemeral, non-persisted) | No target / DEPRECATE or REPLACE-if-scoped-later | Confirm with M-03 whether real persisted live chat is in v1 scope; if not, this capability is dropped with an explicit deprecation entry (it was never really functional in R25 either — no user-facing regression from removing a non-functional mock). |
| `docker-compose.yml` planned `postgres`/`backend`/`frontend` services, `.env`'s unused `POSTGRES_PASSWORD`/`JWT_SECRET` | No target — discard | Confirmed unused by any code (M-01 finding). Not part of the migration; new environment config is defined fresh in M00. |
| `manifest.json` PWA metadata | Next.js `app/manifest.ts` (or static `public/manifest.json`) | Direct copy of name/icons/theme-color/lang, re-expressed per Next.js conventions. |
| `sw.js` + self-defeating cache-buster (index.html:4-24) | Next.js PWA strategy (if any) designed fresh in M09 | Do not port the contradiction (SW that's immediately unregistered) — explicit fresh decision required, documented as a REPLACE in the parity matrix (M-03), not a port. |
