## Audit trail note (item 7)

Live verification of `recordAuditLog`/`listAuditLog` initially appeared to show a bug: writes reported success (`status: 201`) but reads (`select=*&order=...&limit=...`) returned `[]`, even though direct SQL confirmed the rows existed. Isolated the cause: this was **entirely an artifact of manual `curl` testing**, not an app bug — the test requests sent only an `apikey` header without `Authorization: Bearer <jwt>`, so Kong/PostgREST resolved the role as anonymous, and `audit_log`'s `admin read` RLS policy (correctly) returned nothing. With both headers present, the same query returns all rows regardless of `order`/`limit`. Separately, a genuine (minor) gap was found: `getRecentAuditLog()` existed and was correctly wired to the real, RLS-protected data, but no admin page ever rendered it — added `src/app/(admin)/admin/audit-log/page.tsx` (+ nav link) this phase. Verified live in-browser as the logged-in admin: all 4 real rows render correctly. Temporary diagnostic logging added to `audit.db.ts` during this investigation has been removed.

## Image optimizer note (item 7)

Every avatar/logo on every real-data page returned an unstyled broken image, confirmed via network requests: `GET /_next/image?url=...127.0.0.1:54321...` → `400 "url" parameter is not allowed`. Initially suspected `next.config.ts`'s `remotePatterns` (added earlier this phase for `127.0.0.1:54321`) was somehow not matching, but the actual cause is a separate, later, unconditional check in Next's image optimizer (`node_modules/next/dist/server/image-optimizer.js`, `isPrivateIp`) — an SSRF guard that rejects any upstream URL resolving to a private/loopback IP, regardless of `remotePatterns`. `127.0.0.1` (how the local Supabase CLI stack serves Storage) always trips this. Real Supabase Storage (staging/production) is never a private IP, so this is a **local-dev-only** condition, not a production security concern to relax. Fixed by setting `images.unoptimized` to `true` only when `NEXT_PUBLIC_SUPABASE_URL` contains `127.0.0.1` (`next.config.ts`) — production keeps full Next.js image optimization; local dev against the CLI stack bypasses the optimizer proxy and lets the browser fetch the image directly. Verified live: both player avatars (e.g. player 18 "Xuân Sử") and all 3 team logos now return `200 OK` and render correctly in-browser (screenshot taken). This was undetectable by any prior gate (unit tests, code review, build) — it only manifests as a real HTTP round-trip against a real image host, exactly the class of bug M12.5 exists to catch.

## Accessibility note (item 7)

Running axe against `/doi` (the first real-data route ever scanned — M12's accessibility gate only covered the Supabase-independent homepage) found a genuine WCAG AA violation: the "OVR" badge's text color for Team X uses `--team-color-x` (`#f5a623`, Xiphias orange) directly, which is only 2.02:1 against a white card (needs 4.5:1); Team P (blue) and Team T (red) both already passed. Root cause: `components/ui/Badge.tsx` used the same brand-accent value for both the border (fine — brand identity) and the text (fails contrast). Fixed by adding a text-safe token, following the same pattern M12 already established for `--text-on-interactive-primary`/`--text-on-prestige-accent`: `--text-on-team-x` (sports.css) defaults to `--ptx-neutral-900`, with a dark-theme override back to the raw brand color in `themes/dark.css` (the dark theme's card surface, `#1e293b`, already gives the raw orange 7.2:1 contrast — computed and confirmed live, not assumed). `Badge` now accepts an optional `textColor` separate from `accentColor`; `TeamCard`/`TeamProfile` pass `getTeamTextColorVar(team.id)`. Verified visually in all 3 themes (light/summer: dark readable text on white; dark: original bright orange, already accessible) and via the automated axe re-run (24/24 passed, see item 7 above). This bug was invisible to M12 because no accessibility scan had ever run against a page rendering a real team.
