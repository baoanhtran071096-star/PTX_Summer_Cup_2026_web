## 2. Admin session / auth state

- Boolean flag `adminLoggedIn`, **no real session/token/expiry** — pure client-side flag.
- Password hashing: SHA-256(salt+password) via Web Crypto (`hashPassword()`, 6719-6739), salt generated by `getSalt()` (6710-6717) using Math.random+Date.now — **not cryptographically strong salt generation**, and no server-side verification. Any DevTools user could bypass client checks; the only real gate is Firestore's `request.auth != null` rule on writes, which doesn't protect anything client-render-only.
- Login lockout: 5 failed attempts → 5-minute lockout (10104-10172).

## 3. Match/live state

Entirely **derived at render time** from `Date.now()` vs. `MATCHES_CONFIG` start/end times, plus parsed `ptx_result_*` strings. **No persisted match-status enum, no server-authoritative clock.** This is a significant gap vs. the planned `matches.status` column in `database_schema.sql:57` and vs. Architecture v1.3's Realtime (M08) requirements — the new platform needs a real authoritative status field and server-driven realtime updates, not client-clock derivation.

## 5. Service worker (`sw.js`)

- Cache name: `ptx-cup-2026-v2-r13`.
- Precaches `index.html`, `manifest.json`, 6 key media assets.
- Strategy: **network-first** for `.html`/`.js`/root requests (always tries fresh, falls back to cache), **cache-first** for other static assets/images.
- On `activate`, purges any cache key other than the current `CACHE_NAME`.
- **⚠ Self-defeating in production**: `index.html` itself immediately unregisters any active service worker and deletes all caches on every load, via an inline cache-buster script at index.html:4-24 (explicit comment: "guarantee fresh R11 release"). This means `sw.js`'s entire caching strategy is currently dead code in practice — flag explicitly for M-03 decision (replace outright with a real Next.js PWA strategy, don't port the contradiction).

## 7. `docker-compose.yml` / `.env` — planned-but-unbuilt backend

Defines services `postgres`, `backend` (`build: ./backend` — **directory does not exist**), `frontend` (`build: ./frontend` — **does not exist**). `database_schema.sql` is mounted into the `postgres` service as init SQL. `.env` contains real values for `POSTGRES_PASSWORD` and `JWT_SECRET` (excluded from `.gitignore`-tracked commits, not reproduced in this audit) — **unused by any code in this repo today**; nothing in `index.html` issues HTTP calls to a backend or reads `DATABASE_URL`/`JWT_SECRET`. Treat as a stale/aspirational scaffold, not live runtime state. Recommend rotating/discarding these secret values rather than carrying them into the new environment configuration.
